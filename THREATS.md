# TrustVault threat model

Each row: what could go wrong, what stops it, the test that proves it (all in `tests/`), and what is left over. "Left over" is stated honestly; nothing here claims to be perfect.

| # | Threat | What stops it | Test | Left over |
|---|---|---|---|---|
| 1 | One user reads or changes another user's document (guessing ids) | Every document route calls `authz.authorize()`; no grant means 404, and the refusal is audited. Search uses the same rule inside the SQL (`visible_documents`) | `test_documents.py::test_no_grant_means_404_and_nothing_changes` (7 routes x 4 people), `test_search.py` | None known; 404 hides existence |
| 2 | The administrator reads document contents | The admin has no access path: `authorize` gives no special case; Documents log and Bin select details only, never the content column | `test_no_grant_means_404...[admin-*]`, `test_accounts.py::test_the_documents_log_shows_details_only_and_filters`, `test_deleted_documents_go_to_the_admin_bin_with_details_only` | The administrator can edit the database directly (see 15) |
| 3 | A viewer does more than they were given | Read grant: open and download only. Edit grant: title, category and file only. Share, delete and revoke are owner-only. Documents can be shared only with viewers | `test_read_grant_allows_view_and_download_only`, `test_edit_grant_can_change_details_but_not_owner_delete_or_share`, `test_documents_can_be_shared_only_with_viewers`, `test_an_editor_can_replace_the_file_and_a_reader_cannot` | None known |
| 4 | Access removed but still works | Access is read from the database on every request; revoke and disable take effect at once; disabling or changing a password raises `session_version` so old cookies die | `test_revoke_works_at_once_in_an_already_logged_in_session`, `test_grant_for_a_user_who_is_later_disabled_stops_working`, `test_change_password_signs_out_other_devices_but_not_this_one` | A document the person already downloaded stays downloaded |
| 5 | Password guessing | Lock-out: 5 failures per username or 20 per address in 15 minutes (checked before the password); same message for wrong user, wrong password and disabled account; dummy hash keeps timing equal | `test_five_failures_lock_the_account_even_for_the_right_password`, `test_one_address_trying_many_usernames_gets_locked`, `test_all_login_failures_look_the_same` | Someone can lock a known username for 15 minutes (accepted: denial of one account) |
| 6 | Weak passwords | Rule: 8+ characters with a capital, a number and a special character, at joining, change and reset | `test_password_rule_at_joining`, `test_change_password_refusals` | No breached-password check |
| 7 | Anyone can create an account | No registration page. Owners join only by an administrator's invitation, viewers only by an owner's. Link: random 256-bit secret, only its SHA-256 is stored, works once (the first write marks it used, so two simultaneous uses cannot both win), expires in 48 hours, a new invitation replaces the old; role and e-mail come from the invitation, not the form | `test_a_used_link_cannot_create_a_second_account`, `test_an_expired_or_made_up_link_is_refused`, `test_the_invited_address_cannot_be_changed_by_the_form`, `test_only_a_hash_of_the_link_is_stored`, `test_the_old_create_user_and_register_pages_are_gone` | Whoever holds the link before the invited person can join as them. If e-mail is not set up, the inviter sees the link on screen and passes it on by hand: only as safe as that channel |
| 8 | "Forgot password" abuse | 6-digit code stored only as an HMAC; 10 minutes; one use; 5 wrong tries block it; 3 codes per person per hour; 5 requests per address per 15 minutes; same answer for unknown addresses; the administrator is excluded; setting the new password ends all sessions. No link is e-mailed, so the Host header cannot poison it | `test_forgot_password_with_a_code_sets_a_new_password`, `test_five_wrong_codes_block_the_right_one`, `test_an_expired_code_is_refused`, `test_unknown_addresses_and_the_admin_get_the_same_answer_and_no_mail`, `test_the_code_is_stored_only_as_a_hash_and_requests_are_limited` | Anyone who controls the person's mailbox can reset their password. A 6-digit code has a million values, so the 5-try limit is what protects it |
| 9 | The administrator account is taken over or replaced | One administrator, set in the database. A trigger raises `session_version` whenever any password hash changes, so replacing the password signs the administrator out everywhere. No e-mail reset for the administrator | `test_changing_a_password_in_the_database_signs_that_user_out_everywhere` | Whoever controls the database controls everything |
| 10 | Forged form posts (CSRF) | Every POST needs the session's token; cookie is `HttpOnly`, `SameSite=Lax`, `Secure` on Render; CSP `form-action 'self'` | `test_login_needs_the_csrf_token`, `test_every_document_form_needs_the_csrf_token`, `test_login_cookie_flags` | None known |
| 11 | Script injection (XSS) | Jinja escapes everything; CSP `default-src 'self'` (no inline script or style); uploaded files served with `nosniff` and a sandbox policy | `test_titles_are_escaped_so_scripts_cannot_run`, `test_download_headers_make_it_a_safe_download`, `test_open_shows_the_file_inline_with_safe_headers` | A PDF is shown by the browser's own viewer without the sandbox flag (PDF viewers do not work inside one) |
| 12 | Harmful uploads | Extension allow-list; contents must match the type (magic bytes, zip structure for Word/Excel, UTF-8 for text); names cleaned (no folders, no markup); files never executed; all-or-nothing per upload; 100 MB total, 50 files, read with a cap so an oversized upload is stopped early | `test_documents.py` (type, size, name, all-or-nothing tests) | No virus scanning. A 100 MB upload is held in memory and may exceed the free plan's 512 MB |
| 13 | SQL injection | Every query uses placeholders; filters add fixed SQL pieces plus parameters; search wildcards are escaped | `test_search.py`, `test_hostile_filter_values_do_not_break_the_page` | None known |
| 14 | Open redirect through a star or notification link | Only paths starting with one `/` are followed | `test_star_redirect_cannot_leave_the_site` | None known |
| 15 | The audit record is altered | Append-only database triggers (no update, delete or truncate); each row holds the hash of the row before it; "Check the chain now" recomputes everything; a failed check raises a security alert | `test_the_database_refuses_to_change_or_remove_audit_rows`, `test_changing_an_old_row_is_detected_at_that_row`, `test_verify_button_reports_tampering` | Cutting off the newest rows, or rewriting the whole chain with every hash recomputed, is not detectable by the chain alone. Someone with database ownership can drop the triggers. Fix would be to export the latest hash somewhere the database owner cannot reach |
| 16 | Unusual behaviour goes unnoticed | The red alert icon: 3 or more wrong passwords, deletions, locked accounts, 3 or more refusals, 10 or more opens/downloads in 10 minutes, a failed chain check; each links to the audit record | `test_wrong_passwords_deletions_and_refusals_raise_alerts_that_can_be_marked_seen`, `test_opening_ten_documents_quickly_is_an_alert` | Thresholds are fixed numbers; alerts show up when the administrator looks, nothing is e-mailed |
| 17 | A deleted document is lost or kept forever | Delete hides it for everyone and moves it to the administrator's bin for 15 days; restore returns it to its owner with the same sharing; after 15 days it is removed for good and logged (`doc.purge`) | `test_restore_one_returns_the_document_to_its_owner_with_its_sharing`, `test_documents_in_the_bin_over_15_days_are_removed_for_good` | The purge runs when the administrator opens the Bin or restores something (no background job on the free plan) |
| 18 | The e-mail service is abused or leaks, or an invitation goes to a wrong address | Only invitations and codes are sent, never document contents; key and sender are server settings, not in the code; failures never raise or log the message | `test_without_a_mail_service_the_inviter_is_shown_the_link`, `test_an_invitation_to_a_domain_that_does_not_exist_is_refused`, `test_the_success_message_does_not_promise_delivery` | A mailbox cannot be checked before sending: only an address whose domain does not exist is refused; a made-up name on a real domain bounces later and the invitation stays Pending. The e-mail provider sees invitation links and codes. E-mail is not end-to-end private |
| 21 | Changing e-mail or username to take over an account | Profile changes need the current password; both must stay unique; changes are audited; changing the e-mail cancels unused reset codes | `test_profile_edit_refusals`, `test_profile_can_be_edited_and_is_recorded` | A person who knows the password can change the e-mail (they already have the account) |
| 19 | Demo credentials are public | They are in the README on purpose so evaluators can sign in | - | Anyone can sign in to the demo. A real deployment must change them (`UPDATE users SET password_hash = ...`) and remove the demo data |
| 20 | Sign-in page and invitation links reach the wrong place | `Referrer-Policy: no-referrer`, `Cache-Control: no-store`, `X-Frame-Options: DENY`, HSTS on Render; invitation links are built from `APP_URL` when set | `test_security_headers_are_on_every_page` | Set `APP_URL` in production, otherwise the link uses the request's host |

## Out of scope / not done
Two-factor sign-in; rate limiting beyond sign-in and the forgot-password form; denial-of-service protection; backups and recovery; encryption of file contents at rest in the database; a security review by a person other than the author.
